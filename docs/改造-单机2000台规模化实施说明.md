## 2. 改动明细

### R1 套接字池动态化（`WLServerTestDlg.cpp`）

- 删除 `SOCKET g_sock[1000]`（越界即内存破坏），改为 `std::vector<SOCKET> g_vecSockTable` + `CCriticalSection g_csSockTable`
- `MAX_SUPPORTED_CLIENTS = 4096`，按实际注册数 `InitSocketTable()` 预分配，越界访问返回 `INVALID_SOCKET`
- `g_nSocketCount` 改 `volatile LONG`，新增槽位用 `InterlockedIncrement` 计数
- **关键修正**：旧代码 `g_sock[g_nSocketCount++] = sock[i]` 会把 socket 写到"线程执行顺序"决定的槽位，而日志线程按 `g_sock[客户端索引]` 读取；池化后线程并发执行，该错槽会被放大。现改为 `SetSocketForClient(pHeapArgs->iArrClientIndex[i], sock[i])`，**按客户端索引写入**，与日志侧读取口径一致。

### R2a 心跳线程池化（`WLServerTestDlg.h` / `.cpp`）

- `HB_CLIENTCOUNT_PER_THREAD`：`1 → 20`；`HBClientCount_InEveryThread`：`10 → 20`（线程栈数组同步扩容）
- 线程数由 `floor` 改 `ceil`：`(iNeedHB_ClientCount + N - 1) / N`，避免非整除时尾部客户端漏发心跳
- 每个线程的 `iClientCount` 改为**实际装载数**（末线程可能 < 20），在线计数同步按实际数累加；不再固定加 20
- 线程启动错峰 `Sleep(500) → Sleep(20)`：2000 台时 100 个线程，总启动时间从 ~50 秒降到 ~2 秒
- 保留 `_New` 路径全部既有修复（devid 竞态、ComputerIP 注入、自动配置上传），未复活 `_Ori` 旧函数（报告 §6.2 的明确要求）

### R3 线程优先级（`WLServerTestDlg.cpp`）

- 日志线程：`THREAD_PRIORITY_TIME_CRITICAL → THREAD_PRIORITY_ABOVE_NORMAL`
- 心跳线程：`THREAD_PRIORITY_NORMAL → THREAD_PRIORITY_ABOVE_NORMAL`
- 两者同级，消除"500 个日志线程饿死心跳线程"的调度基础。**按假说处理，必须在 2000 规模实测确认**，不可当作已解决。

### R4 心跳内同步 HTTPS 剥离（`WLServerTestDlg.cpp`）

- 收到 `cmd=17 POLICY` 不再在心跳线程内同步调用 `SendHeartbeat()`（HTTPS 取策略），改为 `EnqueuePolicyFetch(客户端索引)`
- 新增单工作线程 `ThreadFunc_PolicyFetchWorker` + 有界队列（容量 4096，50ms 轮询）；`OnDestroy` 置停止标志
- 一个终端的 HTTPS 阻塞不再拖累同一 heartbeat 线程里的其余 19 个终端

### R5 注册并发限流（`WLServerTestDlg.cpp`）

- 删除"每客户端一个注册线程 + `Sleep(20)` 错峰"（2000 台 = 2000 个瞬时线程 + 40 秒错峰）
- 改为固定 **32 个**注册工作线程，按索引切片消费 `g_vecAllClientObjects`，复用原 `ThreadFunc_Register_SameTime` 的全部重试/devid 逻辑
- 注册成功/失败计数、UI 刷新逻辑保持原语义（`g_iThreadCount_RegSameTime` 现表示"并发注册中的客户端数"）

### R6 共享资源健壮性（`WLServerTestDlg.cpp`）

- 心跳首次建连、两次重连点（HB 失败重连 / `NOREGISTER` 后重连）均调用 `SetSocketForClient()` 发布最新 socket
- 日志线程每次发送轮次开始用 `GetSocketForClient(客户端索引)` 刷新 socket，修复"心跳重连后日志线程仍持有旧 socket"
- 初始建连时 `ClearSocketTable() + InitSocketTable()`，避免二次注册残留旧槽位
- 界面下拉补 `2000` 选项（心跳客户端数、日志任务客户端数）

## 4. 验收计划（必须实机闭环，未执行）

报告 §6.3 明确：**以平台入库实测 + 24h soak 为准，不用工具侧"成功数"或理论 EPS 下结论**。

1. **前置确认**：平台 watchdog 约 90s、平台总部署规模、单机动态端口范围与 `TimedWaitDelay`（短连接场景）
2. **阶段一基线**：本机 500 / 1000 / 1500 / 2000 台，**纯心跳**（不开日志），每档至少 30 分钟，记录在线数与平台侧 session
3. **阶段二**：2000 台 + 日志压力，从 500 EPS/主机逐步上探到 ~5460 EPS/主机，观察掉线、EPS 与平台入库量
4. **稳定性**：通过档位做 24 小时 soak，对比工具计数与平台 Flume 入库
5. **停止/重连回归**：任务停止响应（不可中断 Sleep 历史坑）、策略/注册重连后日志是否继续发送（R6）
6. **判定**：任一档出现心跳掉线或平台入库不达标 → 回退该档，按报告 §4 推进 R2b 或 R2c，不得靠"降档跑通"宣称 2000 台达成

## 5. 已知限制与风险

- **R2b 未实施**：日志仍是 1 线程/终端。2000 台 + 日志时线程数仍可能成为瓶颈；阶段二压测若在此触顶，需按报告"每轮批量 + 每 clientId 队列 + 单写端"思路做日志池化（对标老工具 4000 EPS 实证，C# 仅作参考）
- **per-socket 发送锁未加**：HB 与日志共享 socket 的并发碰撞在 2000 台下期望约每 90 秒一次；本次通过"按客户端索引发布最新 socket"消解了错槽，但未对同一 socket 的并发 `send` 加锁，属于剩余风险
- **R3 未压测验证**：同级优先级只是消除饿死的必要条件，提升幅度未知
- **注册并发 32 是保守值**：平台注册接口的并发窗口需与平台侧确认；过高可能打爆接口
- **V6.9.1 是分支版本**：未合并 `main`，未打 tag；发布包在本机 `artifacts/`（gitignore，不入库）。V6.9.0 产物原样保留，不使用覆盖方式更新。
- **无实机环境**：本次只完成静态改造 + 编译/打包验证，不能宣称"2000 台已可用"
