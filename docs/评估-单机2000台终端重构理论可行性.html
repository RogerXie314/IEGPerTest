1. 目标与前提假设

1.1 目标

  • 用 5 台主机稳定模拟 10000 台终端，即每台主机需稳定承载 2000 台。
  • “稳定”定义为：压测全程心跳不批量掉线；开启日志时日志曲线（EPS）平稳，无级联断连。

现行 WLServerTest 是 MFC 单进程 GUI 压测工具，其“客户端模拟”核心由两条线程链构成：注册链、心跳链，外加按需叠加的日志链。以下为决定单机上限的四类约束，均已在源码中定位。

4. 重构路径逐条理论可行性推演

按“解除约束 → 稳定调度 → 压降 CPU”三个层次，共梳理 6 条路径。每条给出：改造内容、理论可行性、工作量、前置依赖与风险。

R1　套接字池动态化 必要 · 低风险

  • 内容：将 g_sock[1000] 改为按目标规模动态分配（如 std::vector<SOCKET> 或 g_sock[4096]），并给 g_nSocketCount 加越界保护、将写入改为 InterlockedIncrement 原子操作。
  • 理论可行性：高。这是纯数据结构扩容，不改变线程/协议逻辑；2000 个套接字对单进程而言远低于系统上限。
  • 工作量：小。
  • 风险：需同时修复 g_nSocketCount++ 的竞态（文档 §差异 4 记录的 socket 泄漏隐患），否则扩容后竞态窗口内的错槽问题会被放大。

R2　线程模型与终端解耦 核心 · 中高工作量

这是把单机从 ~500 台推向 2000 台的关键路径，含三档方案，可按成本递进：

档位做法理论可行性备注
R2a 心跳线程池化 把 HB_CLIENTCOUNT_PER_THREAD 由 1 提高到 N（如 10–50），并相应扩大 HBClientCount_InEveryThread（现为 10）。一个线程在一轮内顺序处理 N 个终端的心跳，然后统一 Sleep(30s)。 高：代码骨架已具备——线程数组已按 HBClientCount_InEveryThread 预申请，线程数按 客户端数 / HB_CLIENTCOUNT_PER_THREAD 计算，循环本身就是多终端结构，只需改常量与数组尺寸。 N=20 时心跳线程 2000→100。心跳间隔 30s，单线程带 10–50 个终端时间上充裕。
R2b 日志线程池化 日志链目前同样是 1 线程/终端。改为线程池，每线程轮转多个终端并按限速发送。 中：日志有每终端 EPS 节奏与子报文间隔逻辑，池化需引入每终端调度状态（对齐 NativeRunner 的“每 clientId 队列 + 单一写端”思路）。 与 R6 的 socket 共享修复一并做更稳妥。
R2c 事件驱动（IOCP） 用 IO 完成端口统一管理全部套接字，心跳/日志发送走完成队列，取消“按终端建线程”。 高（长期最优）：单机数千连接的标准解法，线程数可压到核数量级，且彻底消除“终端数 = 线程数”的线性膨胀。 工作量最大，属于架构级重写；建议在 R2a/R2b 验证到瓶颈后再评估。

依赖：R2 必须先有 R1（套接字池足够大），否则池化后仍会撞 1000 上限。

R3　线程优先级与调度修复 必要 · 低风险

  • 内容：把日志线程由 THREAD_PRIORITY_TIME_CRITICAL 降为 ABOVE_NORMAL，与心跳线程同级调度（NativeRunner 已如此处理）。
  • 理论可行性：高。项目文档已论证：原 TIME_CRITICAL + NORMAL 组合下，500 个日志线程每 50ms 唤醒一次会长时间饿死心跳线程；同级后改为公平轮转。
  • 注意：文档明确此改动“尚未完成压测验证”——可行性有理论支撑，但稳定性提升幅度必须由实测确认。

R4　解除心跳线程内的同步 HTTPS 阻塞 重要 · 中工作量

  • 内容：收到 cmd=17 POLICY / cmd=18 NOREGISTER 时，不在心跳线程内同步发起 HTTPS，而是投递到独立工作线程/队列（可借鉴 NativeRunner 用 stdio 交给控制侧处理的做法）。
  • 理论可行性：高。属于职责下沉，不改变协议语义。
  • 依赖/风险：若采用 R2c 事件驱动，此问题自然消解；若走 R2a 池化，则需显式剥离，否则一个线程下的 N 个终端都会被其 HTTPS 阻塞拖累。

R5　注册并发限流 建议 · 中低工作量

  • 内容：把“每客户端一个注册线程”改为固定并发度的注册池（如 20–50 并发），去掉 Sleep(20) 硬错峰。
  • 理论可行性：高。2000 个瞬时线程的启动冲击会被摊平；注册是初始化一次性动作，不影响稳态。
  • 风险：注册并发度过高会打爆平台注册接口，需与平台侧确认窗口。

R6　协议与共享资源健壮性 建议 · 中低工作量

  • 内容：① g_nSocketCount 原子化；② 停止信号 g_bStopTask 加内存屏障（volatile/Interlocked）；③ 修复“心跳重连后 g_sock[i] 与日志线程持有的旧 socket 失效”的既有缺陷；④ HB/日志共享同一 socket 的发送加 per-socket 锁。
  • 理论可行性：高，逐条均为局部修复。
  • 风险/边界：HB 与日志共享 socket 的并发碰撞，单 socket 每周期概率极低（约 0.017%），但终端数放大到 2000 后，全机每周期出现碰撞的期望次数升到约 0.3 次（≈每 90 秒一次）——数量级虽不致命，但应显式加锁或改为独立连接，不能再沿用“数量少所以不锁”的旧假设。

5. 组合方案与阶段建议

阶段目标必须完成的路径预期可达
阶段一：解除硬约束 让单机“能”跑 2000 台 R1 + R3 + R5 心跳保活口径 2000 台理论上可达；日志压力口径预计仍受 400–500 台历史瓶颈影响
阶段二：解耦线程 让单机“稳”跑 2000 台 阶段一 + R2a/R2b + R4 + R6 心跳 2000 台稳定 + 日志压力具备可行性（线程数降到数百级）
阶段三：架构升级（可选，非首选） 仅当阶段二仍触及上限时再评估 阶段二 + R2c（IOCP） 单机余量充足，可持续演进

建议：先做阶段一（成本最低、直接解除 1000 硬上限），用一次 2000 台心跳压测取得基线；再据日志压测结果决定是否推进阶段二。阶段划分以「复用项目自身已验证的设计」为准则，不首选从零事件驱动重写（依据见第 6 节「历史弯路对照」）。

6. 历史弯路对照与修正（避免重蹈覆辙）

在给出结论前必须先说明一件事：这条 2000 台的路，项目已经走过大半，但“走过”的方式与直觉相反。C++ 老工具在 6 台×500 的配置下实跑过 3000 心跳 + 4000 EPS 且平台非瓶颈；而同一时期，C# SimulatorApp 恰恰是在日志压力下落线的一方（BUG-2026-001：2000 客户端 + 日志，根因在 C# 发送侧），其修复仅验证到 1000 EPS，随后团队放弃 C# 路线、退回基于原始代码树的老工具（C++）继续改造。因此可靠的基线是老工具（C++），不是 C#——这一点直接决定本方案该对标谁。

R2b 日志池化把 C# 当作“已验证权威”去移植——但 C# 正是日志压力下被淘汰的一方，其修复仅验证到 1000 EPS思路可借鉴 C# 的“每轮批量 + 每 clientId 锁 + 单写端”，但基线对标是老工具（C++）在 4000 EPS 下的实证，不是 C#；C# 只作参考不作依据
R2c 事件驱动（IOCP）从零重写，重演“过早理论推导”与 C# 教训降为后续可选项；不首选从零重写，优先复用已验证设计
R3 优先级修复把它当成“已解决”，忽略“未压测验证”按假说处理，必须在 2000 规模实测确认
R1 扩容 / R6 原子化扩容后放大 g_nSocketCount++ 竞态与不可中断休眠同批修复原子计数、停止信号屏障、可中断休眠
验证方法用工具侧“成功数”当验收（已知虚高）以平台入库实测为准 + 24 小时 soak（对齐 BUG-2026-001 验证口径）

6.3 修正后的对标与路线

  • 总原则修正为“回归老工具（C++）基线 + 分阶段外推验证”。对标对象是已经在 4000 EPS 下被证明的 C++ 老工具，不是被淘汰的 C#；“从零 IOCP 重写”降为最后手段。
  • 阶段一（解除硬约束）：R1 套接字池扩容 + R6 原子化/可中断 + R5 注册限流。
  • 阶段二（解耦线程，对齐老工具已验证机制）：R2a 在 _New 路径池化（老工具 HB 本就是每线程多客户端）+ R2b 借鉴 C# 的批量/单写端思路 + R3 同级优先级 + R4 剥离同步 HTTPS。
  • 阶段三（可选）：R2c IOCP，仅当阶段二仍触及上限。
  • 验收：每个阶段都以平台入库实测 + 24h soak 收口，不用理论 EPS 或工具计数下结论。

6.4 可靠性判定——本方案到底靠不靠谱

把方案拆成“方向”与“量级”两件事来判断，结论并不相同：

判断项结论依据
技术方向（解耦线程、扩容套接字、修优先级、复用老工具机制）站得住与项目历史一致：老工具 HB 本就是每线程多客户端，且它是在 4000 EPS 下被证明稳定的那一方
把 C# 设计当“已验证参照”不成立，已修正C# 在日志压力下落线、修复仅验证到 1000 EPS、并被放弃；对标应是老工具
“2000 台/主机”本身无历史先例，属高风险外推历史最高只演示到 500 台/主机（老工具 6×500）；2000 台是 4 倍外推
目标日志吞吐“≈5460 EPS/主机”远超任何验证点，属高风险外推老工具 4000 EPS 是 4 台合计（≈1000 EPS/主机）；C# 修复仅 1000 EPS；目标是其约 5.5 倍

一句话：方案的方向靠谱，但“2000 台/主机 + 5460 EPS/主机”不是“回归已验证”，而是把已验证基线（老工具 500 台/主机、~1000 EPS/主机）向上外推约 4–5.5 倍。这一外推必须被视为高风险、需分阶段实测证伪，而不能定性为“已证明可行”。

7. 关键风险与边界条件

#风险/边界影响应对
1日志 CPU 与 EPS 目标2000 台 × 2.73 EPS ≈ 5460 EPS/主机，可能超出核数承载据此确认服务器核数，或下调每客户端 EPS / 采用池化降开销
2Thread-critical 修复未经实测降优先级能否真正消除掉线，尚无压测结论阶段一后立即做 2000 台心跳压测取证
3平台侧 10000 长连接承载平台若对单 IP/单机连接数有限制，客户端再稳也无法上线与平台确认连接数、注册速率与超时阈值
4跨主机 ClientId 冲突同 ClientId 心跳互踢 session，导致批量掉线5 台各分配独立序号段（README 已明确）
5共享 socket 并发碰撞（见 R6④）2000 台规模下期望约每 90 秒一次碰撞加 per-socket 锁或拆独立连接
6端口耗尽（重连 churn）频繁重连叠加 TIME_WAIT 可能耗尽动态端口延长重连间隔、必要时调整动态端口区间
7每终端 1 线程的“隐性”假设任何残留的 1:1 建线程路径都会把线程数重新推高改造后专项检查全部 AfxBeginThread 调用点

8. 结论

  • 理论可行性成立，但分两个口径：心跳保活口径“可行且改动小”；心跳 + 日志压力口径“可行但受 CPU 与限速粒度主导”，必须实测确认。
  • 现状为零改造不可行：硬上限 1000 与 400–500 台实测崩溃两条证据共同否决了“不改代码直接上 2000 台”。
  • 关键改造集中在三点：套接字池动态化（R1）、线程与终端解耦（R2）、线程优先级与阻塞修复（R3/R4）。其中 R2 是决定单机能否从 ~500 台跨到 2000 台的核心。
  • 最重要的修正——“回归”这一半成立，“移植 C# 设计”这一半不成立：可靠的基线是 C++ 老工具（实测 500 台/主机、4 台合计 4000 EPS 稳定），而 C# 版本恰恰是日志压力下掉线并被放弃的一方（其修复仅验证到 1000 EPS）。因此应以老工具为对标，C# 的批量/单写端思路只作参考；R2c（IOCP）不首选从零重写，仅在阶段二仍触顶时再评估。
  • 可靠性的边界必须讲清：“2000 台/主机”是历史已验证水位（约 500 台/主机）的 4 倍外推，目标日志吞吐（≈5460 EPS/主机）是已验证水位（约 1000 EPS/主机）的约 5.5 倍——因此本方案应定性为“方向可行、量级高风险、需分阶段实测证伪”，而非“已证明可行”。
  • 验收口径对齐历史教训：以平台入库实测 + 24 小时 soak 为准（工具侧“成功数”已知虚高），并把平台 watchdog（约 90s）、平台既有部署规模、短连接端口/TIME_WAIT 作为硬边界先行确认。
  • 综合定性：理论可行、需实测闭环——方向已被项目内部（NativeRunner 与 BUG-2026-001）验证过，不足是“尚未在 2000/主机规模完成压测闭环”。
